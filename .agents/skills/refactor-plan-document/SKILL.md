# DreamSenker 文档写作规范

当用户要求在 `Assets/Documentation` 下创建、整理、改写文档时使用本 Skill。

根据目标目录选择规范：

```text
Assets/Documentation/思路整理 -> 使用“思路整理文档规范”
Assets/Documentation/规划文档 -> 使用“规划文档规范”
Assets/Documentation/参考文档 -> 暂无固定规范
Assets/Documentation/说明文档 -> 暂无固定规范
```

不要把不同目录的写法混用。

## 通用规则

- 使用中文。
- 结论先行。
- 写给用户看，不是写给 AI 看。
- 不写空话、背景论文、过度解释。
- 不复述用户原话当正文开头。
- 不为了显得完整把简单内容展开成长文。
- 用户说“不要动原文件”时，必须新建文档，不覆盖原文档。
- 默认只修改用户要求的文档文件。
- 不修改 Prefab、Scene、ScriptableObject、`.asset`、`.unity`、`.meta` 等 Unity 资产文件，除非用户明确要求。

## 思路整理文档规范

适用场景：

- 用户要求在 `Assets/Documentation/思路整理` 下写文档。
- 用户正在梳理某个系统、功能、调用关系、设计想法。
- 文档目的是帮助用户快速看懂“这件事怎么设计、涉及哪些结构、下一步怎么做”。

参考示例：

```text
Assets/Documentation/思路整理/任务系统条件设计整理.md
```

参考它的组织方式，不照抄具体内容。

### 写作目标

思路整理文档必须短、清楚、能扫读。

重点回答：

- 目标是什么。
- 当前推荐结构是什么。
- 涉及哪些类、枚举、字段、方法。
- 主要流程怎么走。
- 哪些事情当前不做。

### 固定结构

按内容选择下面结构。不要机械凑章节。

```markdown
# <系统或功能名>整理

## 目标

## 基本流程

## 新增枚举

## 新增数据结构

## 新增管理器或核心类

## 修改现有类

## 配置示例

## 暂不做
```

如果某部分不存在，就删掉，不要硬写。

### 目标

放在开头，1 到 3 段。

写清楚：

- 这份文档解决什么问题。
- 当前设计的核心方向。
- 不要在这里塞细节解释。

错误写法：

```text
QuestState 只保存长期状态，不保存当前是否可交付这种动态结果。
```

这种细节应该放到对应结构下面，不要放在目标区。

### 基本流程

用短流程图，不写长段落。

推荐格式：

```text
玩家操作
-> 系统判断
-> 打开面板
-> 调用 Manager
-> 改变数据
```

只写主链路。分支太多时拆成多个小流程。

### 类、枚举、字段、方法结构

如果用户要求写具体结构，代码块里必须给出字段和方法注释。

示例：

```csharp
public class XxxData
{
    // 数据唯一 ID
    [SerializeField] private string _id;

    // 获取数据唯一 ID
    public string Id => _id;

    // 设置数据状态
    public void SetState(EXxxState state);
}
```

要求：

- 每个字段要有注释。
- 每个属性要有注释。
- 每个方法要有注释。
- 枚举项要有注释。
- 注释要短，不写“此字段用于表示一个……”这类废话。

### 修改现有类

只写关键改动。

推荐格式：

标题用 `### XxxClass`，下面直接给结构代码：

```csharp
public class XxxClass
{
    // 当前对象持有的配置
    private XxxDefinitionSO _definition;

    // 初始化当前对象
    public void Initialize(XxxDefinitionSO definition);
}
```

不要机械写“改动前 / 改动后”。只有容易误解时才写。

### 配置示例

配置型系统必须给一两个具体示例。

推荐格式：

```text
XxxConditionSO
Target = 某任务
ExpectedValue = true
```

示例用于说明用户在 Inspector 里该怎么配，不要写成理论解释。

### 暂不做

放文档最后。

只列当前明确不做的东西。

禁止把“暂不做”写成后续需求池。

### 思路整理禁忌

- 不写长篇背景。
- 不把实现计划写成规划文档。
- 不把所有未来功能都塞进来。
- 不在目标区解释细枝末节。
- 不为了完整列出无关类。
- 不覆盖用户原文档，除非用户明确要求。

## 规划文档规范

适用场景：

- 用户要求在 `Assets/Documentation/规划文档` 下创建文档。
- 用户要求为某项功能或系统制定较大的重构方案。
- “较大重构”通常指预计涉及改动脚本大于 3 个。

触发后必须创建文档：

```text
Assets/Documentation/规划文档/<功能或系统名>重构方案.md
```

不要只在对话里给方案。

参考示例：

```text
Assets/Documentation/规划文档/地图系统职责拆分重构方案GPT版本.md
```

参考它的组织方式，不照抄具体内容。

### 规划文档核心原则

方案文档必须短、清晰、可执行。

目标是让用户一眼看懂：

- 为什么做。
- 做完有什么效果。
- 改哪些脚本。
- 按什么顺序做。
- 怎么验证算完成。

### 规划文档固定结构

```markdown
# <功能或系统名>重构方案

## 计划说明

## 结论

## 最终结构

## 改动清单

## 执行顺序

## 验证

## 禁止项
```

### 计划说明

放在文档开头，给用户快速判断这份方案在做什么。

必须包含：

- 本次计划要解决的具体问题。
- 执行后的好处。
- 执行后代码或流程会产生什么效果。

控制在 1 到 3 段。

### 结论

写清楚本次方案的边界。

必须包含：

- 本次要做什么。
- 本次不做什么。
- 哪些行为保持不变。
- 如果分阶段，明确定义当前阶段和后续阶段。

### 最终结构

写重构后的模块分工和依赖方向。

必须包含：

- 关键类或脚本的职责。
- 主要调用链。
- 数据流向。
- 非显然标识符的类型和来源。

优先使用简短结构图。

```text
Controller
  -> Service
  -> Data
```

依赖关系必须准确，不要把真实调用关系写成并列关系。

### 改动清单

这是规划文档核心。

按“新增 / 修改 / 删除 / 不修改”分组列出脚本。

只列脚本改动。不要把 Prefab、Scene、ScriptableObject、`.meta` 或其他 Unity 资产文件写进重构执行计划。

如果脚本删除或移动可能涉及 `.cs.meta`：

- 不要把处理 `.cs.meta` 写成默认执行步骤。
- 只能写“执行前需向用户确认是否处理对应 `.cs.meta`”。
- 不能为了保持工作区干净、引用完整或符合 Unity 常规而默认处理 `.meta`。

每个脚本默认只写：

- 文件路径。
- 2 到 6 条关键改动。

复杂、高风险、容易误解的脚本，才补充“现状 / 调整后”。

如果方案中出现事件名、枚举值、接口名、配置字段、状态机动作、谓词、数据类等非显然标识符，必须写清楚它是什么和定义来源。只解释一次，后文不要反复解释。

推荐格式：

```markdown
### 新增

- `Assets/.../Xxx.cs`
  - ...

### 修改

- `Assets/.../Yyy.cs`
  - ...

### 不修改

- `Assets/.../Zzz.cs`
  - 保持现有职责，只作为调用入口。
```

### 执行顺序

写实际执行顺序，不要只列模块名。

要求：

- 按风险从低到高或依赖从底层到上层排列。
- 每一步要能独立验证。
- 不要把多个大步骤揉成一句。
- 通常控制在 5 到 10 步。
- 每一步只写一行。

### 验证

写清楚本方案完成后的验收标准。

必须包含：

- 关键引用检查，例如 `rg Xxx`。
- `git diff --check`。
- Unity Console Error / Exception 检查。
- 具体运行流程验证，写到用户能照着走。

如果当前项目没有对应自动化测试，不要编造测试。

### 禁止项

放文档最后，明确本次方案的边界。

必须包含：

- 不修改 Prefab、Scene、ScriptableObject、`.asset`、`.unity`、`.meta` 等 Unity 资产文件，除非用户明确要求。
- 不顺手清理、恢复、补齐 `.meta`。
- 不把后续阶段内容塞进当前阶段。
- 不扩大用户要求的重构范围。

禁止项不能反向塞新需求，也不能改变主方案。
