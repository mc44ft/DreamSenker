# 重构方案文档

当用户要求为某项功能或系统制定较大的重构方案时使用本 Skill。

“较大重构”的判断标准：

- 预计涉及改动脚本大于 3 个。

触发后必须创建文档：

```text
Assets/Documentation/规划文档/<功能或系统名>重构方案.md
```

不要只在对话里给方案。

## 参考示例

写新方案前，优先参考这份短版结构：

```text
Assets/Documentation/规划文档/地图系统职责拆分重构方案GPT版本.md
```

参考它的组织方式，不要照抄具体内容。重点学习：

- 开头先写“计划说明”，让用户快速看懂目的和收益。
- 用“结论”明确当前阶段做什么、不做什么。
- 用结构图说明调用关系，避免职责关系写乱。
- 改动清单只写关键脚本和关键动作，不机械展开每个脚本的前后对比。
- 验证标准写成能直接执行或手动检查的清单。

## 核心原则

方案文档必须短、清晰、可执行。它不是论文，目标是让用户一眼看懂：

- 为什么做。
- 做完有什么效果。
- 改哪些脚本。
- 按什么顺序做。
- 怎么验证算完成。

禁止：

- 提前写可选功能。
- 写模糊计划。
- 写“可以考虑”“后续也许”这类不确定方案。
- 把多个互斥方案混在主执行计划里。
- 只写原则，不写具体脚本改动。
- 为了显得完整，把简单内容展开成大段解释。
- 每个脚本都机械写“改动前 / 改动后”。
- 在重构方案里安排修改 Prefab、Scene、ScriptableObject、`.asset`、`.unity`、`.meta` 等 Unity 资产文件，除非用户明确要求。
- 把创建、删除、修改 `.meta` 文件写成默认执行项。

如果用户没有指定文件名，按系统名自动命名。

## 固定结构

文档必须按下面顺序组织：

```markdown
# <功能或系统名>重构方案

## 计划说明

## 结论

## 最终结构

## 改动清单

## 执行顺序

## 验证

## 禁止项
```

## 各部分写法

### 计划说明

放在文档开头，给用户快速判断这份方案在做什么。

必须包含：

- 本次计划要解决的具体问题。
- 执行后带来的好处。
- 执行后代码或流程会产生什么效果。

控制在 1 到 3 段，不写背景论文。

### 结论

写清楚本次方案的边界。

必须包含：

- 本次要做什么。
- 本次不做什么。
- 哪些行为保持不变。
- 如果分阶段，明确定义当前阶段和后续阶段。

### 最终结构

写重构后的模块分工和依赖方向。

必须包含：

- 关键类或脚本的职责。
- 主要调用链。
- 数据流向。
- 非显然标识符的类型和来源。

优先使用简短结构图。依赖关系必须准确，不要把真实调用关系写成并列关系。

```text
Controller
  -> Service
  -> Data
```

### 改动清单

这是文档核心。

按“新增 / 修改 / 删除 / 不修改”分组列出脚本。

只列脚本改动。不要把 Prefab、Scene、ScriptableObject、`.meta` 或其他 Unity 资产文件写进重构执行计划。需要组件约束时，优先写代码侧 `[RequireComponent]` 或运行时初始化策略。

如果脚本删除或移动可能涉及 `.cs.meta`：

- 不要把处理 `.cs.meta` 写成默认执行步骤。
- 只能写“执行前需向用户确认是否处理对应 `.cs.meta`”。
- 不能为了保持工作区干净、引用完整或符合 Unity 常规而默认处理 `.meta`。

每个脚本默认只写：

- 文件路径。
- 2 到 6 条关键改动。

只有复杂、高风险、容易误解的脚本，才补充“现状 / 调整后”。不要对每个脚本机械展开。

如果方案中出现事件名、枚举值、接口名、配置字段、状态机动作、谓词、数据类等非显然标识符，必须写清楚它是什么和定义来源。只解释一次，后文不要反复解释。

示例：

- 写 `E_EventType.Player_HealthUpdate`，并说明它是 `E_EventType` 里的事件类型枚举值。
- 写 `EPredicate.Dead`，并说明它是状态机条件枚举值。
- 写 `PlayerHealthUpdateEventArgs`，并说明它是事件参数数据结构。
- 不要只写 `Player_HealthUpdate` 这种裸名字。

推荐格式：

```markdown
### 新增

- `Assets/.../Xxx.cs`
  - ...

### 修改

- `Assets/.../Yyy.cs`
  - ...

### 不修改

- `Assets/.../Zzz.cs`
  - 保持现有职责，只作为调用入口。
```

复杂脚本才使用：

```markdown
### `Assets/.../Xxx.cs`

现状：

- ...

调整后：

- ...
```

### 执行顺序

写实际执行顺序，不要只列模块名。

要求：

- 按风险从低到高或依赖从底层到上层排列。
- 每一步要能独立验证。
- 不要把多个大步骤揉成一句。
- 通常控制在 5 到 10 步。
- 每一步只写一行。

### 验证

写清楚本方案完成后的验收标准。

必须包含：

- 关键引用检查，例如 `rg Xxx`。
- `git diff --check`。
- Unity Console Error / Exception 检查。
- 具体运行流程验证，写到用户能照着走。

如果当前项目没有对应自动化测试，不要编造测试。

### 禁止项

放文档最后，明确本次方案的边界。

必须包含：

- 不修改 Prefab、Scene、ScriptableObject、`.asset`、`.unity`、`.meta` 等 Unity 资产文件，除非用户明确要求。
- 不顺手清理、恢复、补齐 `.meta`。
- 不把后续阶段内容塞进当前阶段。
- 不扩大用户要求的重构范围。

禁止项不能反向塞新需求，也不能改变主方案。

## 写作风格

- 使用中文。
- 结论先行。
- 具体到脚本和调用链。
- 不写空话。
- 不扩大用户要求的重构范围。
- 能一页写清楚就不要写两页。
- 不追求“完整解释”，追求“用户能照着执行”。
