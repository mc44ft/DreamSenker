# 重构方案文档

当用户要求为某项功能或系统制定较大的重构方案时使用本 Skill。

“较大重构”的判断标准：

- 预计涉及改动脚本大于 3 个。

触发后必须创建文档：

```text
Assets/Documentation/规划文档/<功能或系统名>重构方案.md
```

不要只在对话里给方案。

## 文档要求

重构方案必须明确、可执行。

禁止：

- 提前写可选功能。
- 写模糊计划。
- 写“可以考虑”“后续也许”这类不确定方案。
- 把多个互斥方案混在主执行计划里。
- 只写原则，不写具体脚本改动。
- 在重构方案里安排修改 Prefab、Scene、ScriptableObject、`.asset`、`.unity`、`.meta` 等 Unity 资产文件，除非用户明确要求。
- 把创建、删除、修改 `.meta` 文件写成默认执行项。

如果用户没有指定文件名，按系统名自动命名。

## 固定结构

文档必须按下面顺序组织：

```markdown
# <功能或系统名>重构方案

## 重构原因

## 重构目标

## 重构完成后的代码结构

## 重构执行计划

## 重构计划执行顺序

## 注意项
```

## 各部分写法

### 重构原因

写清楚为什么要重构。

必须包含：

- 当前代码的具体痛点。
- 痛点对应到哪些脚本或调用链。
- 不重构会带来的维护问题。

### 重构目标

写明确的完成标准。

必须包含：

- 重构后要消除什么问题。
- 哪些行为保持不变。
- 哪些职责要重新归属。

### 重构完成后的代码结构

写重构后的模块分工和依赖方向。

必须包含：

- 关键类或脚本的职责。
- 主要调用链。
- 数据流向。
- 非显然标识符的类型和来源。

可以用简短结构图：

```text
Controller
  -> Service
  -> Data
```

### 重构执行计划

这是文档核心。

必须逐个列出要改的脚本，并写清楚每个脚本的改动项。

只列脚本改动。不要把 Prefab、Scene、ScriptableObject、`.meta` 或其他 Unity 资产文件写进重构执行计划。需要组件约束时，优先写代码侧 `[RequireComponent]` 或运行时初始化策略。

如果脚本删除或移动可能涉及 `.cs.meta`：

- 不要把处理 `.cs.meta` 写成默认执行步骤。
- 只能写“执行前需向用户确认是否处理对应 `.cs.meta`”。
- 不能为了保持工作区干净、引用完整或符合 Unity 常规而默认处理 `.meta`。

每个脚本都要包含：

- 文件路径。
- 改动项。
- 改动前的大体逻辑。
- 改动后的大体逻辑。

如果方案中出现事件名、枚举值、接口名、配置字段、状态机动作、谓词、数据类等非显然标识符，必须写清楚它是什么和定义来源。

示例：

- 写 `E_EventType.Player_HealthUpdate`，并说明它是 `E_EventType` 里的事件类型枚举值。
- 写 `EPredicate.Dead`，并说明它是状态机条件枚举值。
- 写 `PlayerHealthUpdateEventArgs`，并说明它是事件参数数据结构。
- 不要只写 `Player_HealthUpdate` 这种裸名字。

推荐格式：

```markdown
### `Assets/.../Xxx.cs`

改动项：

- ...

改动前：

- ...

改动后：

- ...
```

### 重构计划执行顺序

写实际执行顺序，不要只列模块名。

要求：

- 按风险从低到高或依赖从底层到上层排列。
- 每一步要能独立验证。
- 不要把多个大步骤揉成一句。

### 注意项

放文档最后。

可包含：

- 重构风险。
- 推荐但本次不执行的另一种重构方式。
- 当前方案的好处。
- 用户可以学到的知识点。

注意项不能改变主方案，不能塞新的可选功能。

## 写作风格

- 使用中文。
- 结论先行。
- 具体到脚本和调用链。
- 不写空话。
- 不扩大用户要求的重构范围。
