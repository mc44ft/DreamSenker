# 业务系统学习重构计划

> 基于现有项目结构，调整重构顺序，以"学业务系统"为核心目标。
> 原则：小改动先行 → 已有雏形的系统练手 → 新建系统综合运用 → 架构迁移收尾。

---

## Phase 1：Health 事件化（预计 1 天）

**目标**：理解事件驱动 vs 轮询的区别，为后续所有系统打基础。

- [ ] Health 组件添加事件：`OnHealthChanged`、`OnDamaged`、`OnDeath`
- [ ] `SpiderController.TakeDamage()` 中的 `if(Health.IsDead)` 改为事件驱动
- [ ] `FoxController` 同步迁移
- [ ] 所有依赖 Health 状态的地方改为订阅事件

**产出**：几乎所有系统都依赖 Health 的事件化，这一步改动最小、收益最大。

---

## Phase 2：背包系统重构（预计 2-3 天）

**目标**：在已有雏形上练习数据结构设计、事件通知、接口抽象。

**现有问题**：
- `InventoryManager` 仅 44 行，只有字典增删查
- 无物品使用逻辑、无分类/堆叠上限、无装备/消耗品区分
- 无事件通知（UI 不知道何时刷新）
- 硬编码：`TaskPanel.DeliverOnClick()` 直接 `RemoveItemFromPackage(E_PackageItemID.Chen)`

- [ ] 添加背包事件：`OnItemAdded`、`OnItemRemoved`、`OnItemUsed`
- [ ] 物品分类体系：消耗品 / 关键道具 / 装备
- [ ] 物品使用接口 `IUsable`
- [ ] 背包 UI 改为事件驱动刷新，移除手动调用
- [ ] 物品堆叠上限逻辑
- [ ] 移除硬编码，为任务系统交互预留接口

**产出**：完整可用的背包系统，理解事件驱动 UI 刷新、接口抽象、数据与表现分离。

---

## Phase 3：任务系统新建（预计 3-4 天）

**目标**：在背包基础上扩展，学习状态机 + 事件驱动的组合运用。

**需求关联**：
- 设计文档中"找到晨露梦核"等任务需要检测背包物品
- 任务面板交付逻辑需要与背包系统解耦

- [ ] 任务数据结构定义（TaskData：任务ID、状态、条件、奖励）
- [ ] 任务状态机：未接取 → 进行中 → 可交付 → 已完成
- [ ] 任务条件系统：检测背包物品、击杀数量、到达地点等
- [ ] 任务事件：`OnTaskAccepted`、`OnTaskProgressChanged`、`OnTaskCompleted`
- [ ] 任务 UI 改为事件驱动
- [ ] 与背包系统交互：条件检测 + 物品扣减走事件，不走硬编码

**产出**：理解状态机在业务系统中的实际运用、多系统间事件通信。

---

## Phase 4：统一状态机迁移（预计 3-5 天）

**目标**：前面练够了，此时改 Spider/Fox 的状态机才能看懂为什么要统一。

- [ ] 设计通用状态机框架（IState、StateMachine、Transition）
- [ ] SpiderController 状态机迁移
- [ ] FoxController 状态机迁移
- [ ] 移除散落在 Update 里的状态判断逻辑
- [ ] 状态切换改为事件触发

**产出**：理解状态机模式在角色控制中的必要性，以及统一框架的价值。

---

## Phase 5：DialogueSystem 扩展（预计 2-3 天）

**目标**：对话系统需要任务系统的条件判断支持，放后面。

- [ ] 对话节点支持条件分支（基于任务状态、背包物品）
- [ ] 对话事件：`OnDialogueStart`、`OnDialogueEnd`、`OnChoiceMade`
- [ ] 对话触发任务接取/完成
- [ ] 对话 UI 改为事件驱动

**产出**：理解多系统协作（对话 ↔ 任务 ↔ 背包），条件系统的设计思路。

---

## 学习原则

| 原则 | 说明 |
|------|------|
| **自己做，AI 辅助** | 架构决策自己下，样板代码可以让 AI 写 |
| **先撞墙再看别人** | 每个系统先自己搭，遇到问题再搜开源参考 |
| **事件驱动优先** | 所有系统交互走事件，不走直接调用 |
| **每完成一个系统就重构** | 做完背包后回头看自己代码，对比开源项目重构一遍 |
