# 动作系统与预输入整理

## 目标

记录玩家攻击、连招、预输入、状态机和 Animator 的分工。

核心方向：状态机管玩法大状态，动作系统管具体招式流程，Animator 管动画表现。

## 核心结论

- 连招不是“按键后立刻播下一段动画”。
- 连招是“记录输入，等角色规则允许时消费输入”。
- 按键不用统一，攻击执行逻辑要统一。
- StateMachine 不应该画每一段攻击动画。
- Animator 不应该承载连招规则和玩法判断。

## 基本流程

起手攻击：

```text
玩家按 J / K
-> InputBuffer 记录输入
-> 当前大状态允许攻击
-> CombatState 消费输入
-> AttackActionRunner 启动对应招式
-> AnimationPlayer 播动画
-> Attacker 按当前招式数据打击
```

连段攻击：

```text
当前招式播放中
-> 玩家提前按 J / K
-> InputBuffer 记录输入
-> 招式进入可接招窗口
-> AttackActionRunner 检查合法输入
-> 消费输入并切到下一招
```

## 预输入

预输入的作用是避免玩家手快导致输入丢失。

预输入不是无限排队，也不是等动画完全播完再执行。

正确判断条件：

```text
输入仍在缓存有效期内
+ 当前动作处于可执行窗口
+ 当前动作允许这个输入派生
= 执行下一招
```

### 起手预输入

角色还不能立刻攻击时，先记录攻击输入。

常见场景：

- 移动中提前按攻击。
- 落地前提前按攻击。
- 受击硬直结束前提前按攻击。
- 闪避结束前提前按攻击。

### 连段预输入

当前攻击还没到接招时间时，先记录下一段输入。

例子：

```text
Light_1 播到 20% 时按 K
-> 缓存 K
-> Light_1 播到 45% 进入连段窗口
-> K 仍未过期
-> 切 Heavy_2
```

## InputBuffer

InputBuffer 负责记录最近一小段时间的关键输入。

关键规则：

- 每个输入带时间戳。
- 输入超过保质期就丢弃。
- 只消费当前动作允许的输入。
- 输入被消费后立刻删除。
- 不保存玩家乱按的全部按键。
- 可以按优先级选择输入。

常见缓存时间：

```text
0.15s - 0.30s
```

## Cancel Window

Cancel Window 表示当前动作什么时候允许切换到别的动作。

它和 InputBuffer 不是一回事：

- InputBuffer 管输入保留多久。
- Cancel Window 管什么时候能执行。

常见窗口：

```text
Light_1:
  ChainWindow = 0.45 - 0.80
  DodgeCancelWindow = 0.60 - 0.90
```

## Combo Rule

Combo Rule 决定当前招式能接什么。

示例：

```text
Light_1
  J -> Light_2
  K -> Heavy_2

Light_2
  J -> Light_3
  K -> Heavy_Finisher

Heavy_1
  K -> Heavy_2
```

判断顺序：

```text
当前招式
-> 当前时间是否在窗口内
-> 缓存里是否有合法输入
-> 查 next rule
-> 切换下一招
```

## 动作数据

每一招应该是数据，不应该写死在状态图里。

常见字段：

```text
ActionId
AnimationName
AttackDamage
HitboxOffset
HitboxSize
HitboxActiveTime
InputBufferTime
ChainWindow
CancelRules
NextActions
```

攻击强度不同，就应该有不同动作数据。

例如第二段重攻击不能只复用轻攻击的 Attacker 配置。

## 状态机分工

StateMachine 只保留玩法大状态。

推荐粒度：

```text
Locomotion
Combat
HitStun
Dodge
Airborne
Dead
```

不要画成：

```text
Light_1 -> Light_2 -> Heavy_2 -> Heavy_Finisher
```

这种图会变成蜘蛛网，也会退化成低配 Animator。

## CombatState

CombatState 是攻击动作入口，不是所有攻击逻辑的上帝脚本。

职责：

- 进入战斗动作状态。
- 驱动当前 AttackActionRunner。
- 判断动作是否结束。
- 处理是否退出到移动、空中、受击或死亡。

不负责：

- 保存所有招式数据。
- 写死每一段连招。
- 直接做攻击检测。
- 直接处理所有输入细节。

## AttackActionRunner

AttackActionRunner 负责具体动作流程。

职责：

- 保存当前 AttackAction。
- 根据输入缓存判断下一招。
- 控制连段窗口。
- 切换当前攻击数据。
- 调用 AnimationPlayer 播动画。
- 通知 Attacker 使用当前招式数据。

## Animator 分工

Animator 只管表现。

负责：

- 播放动画。
- 动画混合。
- 动画过渡。
- 动画事件。

不负责：

- 连招合法性。
- 输入缓存。
- 攻击优先级。
- 受击打断规则。
- 招式派生规则。

## Attacker 分工

Attacker 只做攻击检测和伤害提交。

它应该读取当前招式数据：

```text
当前伤害
当前攻击范围
当前击退方向
当前命中层级
```

动画事件可以通知 Attacker 在指定帧执行检测。

## 按键设计

按键不需要统一。

推荐输入语义：

```text
J -> LightAttack
K -> HeavyAttack
```

统一的是攻击处理流程：

```text
LightAttack / HeavyAttack
-> InputBuffer
-> Combo Rule
-> AttackActionRunner
```

不要因为想简化状态机，就把所有攻击强行改成一个按键。

## 商业项目常见结构

常见拆分：

```text
Input
-> InputBuffer
-> CharacterStateMachine
-> CombatState
-> Ability / Action System
-> Animator
-> Hitbox / Damage System
```

玩家控制器通常不用行为树做主结构。

行为树更适合：

- 敌人 AI 决策。
- Boss 技能选择。
- 巡逻、追击、逃跑。
- 条件分支复杂的非玩家角色。

## 暂不做

- 不把每一段攻击画成 StateMachine 节点。
- 不把连招规则塞进 Animator Transition。
- 不把所有攻击逻辑写进一个脚本。
- 不用行为树重做玩家控制器。
